# Guia de atualização para 2.0

A versão 2.0 adicionou muitas funcionalidades poderosas. Se você já possui um projeto em uso no ambiente de negócios e criado com base no projeto Skeleton oficial na versão 1.1, pode ajustar seu projeto Skeleton conforme os pontos abaixo. Se for um projeto novo, basta criar um novo projeto com o comando `composer create-project hyperf/hyperf-skeleton` conforme a documentação para usar o novo código do skeleton da versão 2.0. Se a versão que você usa atualmente for inferior a 1.1, será necessário primeiro atualizar para 1.1 e depois, seguindo este guia, atualizar para a versão 2.0.

## Atualizar o Swoole para 4.5+

A versão 2.0 elevou o requisito mínimo de versão do Swoole de 4.4+ para 4.5+. Existem algumas diferenças sutis de uso entre essas duas versões; o Hyperf já se adaptou a essas diferenças em versões anteriores, então você pode ignorar os detalhes dessas diferenças. Elevar a versão do Swoole para 4.5+ serve principalmente para reduzir o impacto de longo prazo que o legado histórico causa ao Hyperf. Você pode executar `php --ri swoole` para verificar a versão do Swoole no ambiente atual e seguir as orientações da [documentação do Swoole](https://wiki.swoole.com/#/environment) para concluir a atualização do Swoole.

## Adicionar inicialização do ClassLoader no arquivo de entrada

A versão 2.0 alterou a lógica subjacente do AOP, portanto é necessário adicionar uma linha de código de inicialização no arquivo de entrada do framework `bin/hyperf.php`. Você precisa adicionar o código `Hyperf\Di\ClassLoader::init();` na primeira linha dentro da função anônima de entrada, conforme mostrado abaixo:

```php
<?php

ini_set('display_errors', 'on');
ini_set('display_startup_errors', 'on');

error_reporting(E_ALL);
date_default_timezone_set('Asia/Shanghai');

! defined('BASE_PATH') && define('BASE_PATH', dirname(__DIR__, 1));
! defined('SWOOLE_HOOK_FLAGS') && define('SWOOLE_HOOK_FLAGS', SWOOLE_HOOK_ALL);

require BASE_PATH . '/vendor/autoload.php';

// Self-called anonymous function that creates its own scope and keep the global namespace clean.
(function () {
    Hyperf\Di\ClassLoader::init();

    /** @var \Psr\Container\ContainerInterface $container */
    $container = require BASE_PATH . '/config/container.php';

    $application = $container->get(\Hyperf\Contract\ApplicationInterface::class);
    $application->run();
})();

```

Enquanto isso, o arquivo de entrada do PHPUnit talvez precise do mesmo tratamento. O arquivo está em `tests/bootstrap.php`, conforme mostrado abaixo:

```php
<?php

declare(strict_types=1);

error_reporting(E_ALL);
date_default_timezone_set('Asia/Shanghai');

! defined('BASE_PATH') && define('BASE_PATH', dirname(__DIR__, 1));
! defined('SWOOLE_HOOK_FLAGS') && define('SWOOLE_HOOK_FLAGS', SWOOLE_HOOK_ALL);

Swoole\Runtime::enableCoroutine(true);

require BASE_PATH . '/vendor/autoload.php';

Hyperf\Di\ClassLoader::init();

$container = require BASE_PATH . '/config/container.php';

$container->get(Hyperf\Contract\ApplicationInterface::class);

```

## Ajustar o `composer.json`

Devido ao ajuste da lógica subjacente do AOP na versão 2.0, o script `init-proxy.sh` foi removido. Portanto, é necessário remover do `composer.json` a instrução de execução `"init-proxy.sh"` dentro de `scripts.post-autoload-dump` e alterar o comando dentro de `post-autoload-dump` para a instrução `rm -rf runtime/container`.

```json
{
    "scripts": {
        "post-root-package-install": [
            "@php -r \"file_exists('.env') || copy('.env.example', '.env');\""
        ],
        "post-autoload-dump": [
            "rm -rf runtime/container"
        ],
        "analyse": "phpstan analyse --memory-limit 300M -l 0 -c phpstan.neon ./app ./config",
        "cs-fix": "php-cs-fixer fix $1",
        "start": "php ./bin/hyperf.php start",
        "test": "co-phpunit -c phpunit.xml --colors=always"
    }
}

```

## Ajustar as versões de dependência do composer.json

Como é necessário atualizar para os componentes da versão 2.0, e o projeto skeleton originalmente depende por padrão dos componentes da versão 1.1.x, precisamos fazer alguns ajustes nas restrições de dependência: alterar a dependência `~1.1.0` de todos os componentes Hyperf originais para `~2.0.0`. Além disso, você também precisa alterar a versão de dependência de `phpstan/phpstan` para `^0.12`. Após as alterações, execute `composer update` para atualizar as dependências para a versão 2.0.

## Ajustar o Dockerfile

Durante o empacotamento da imagem Docker, executar ativamente o comando `php bin/hyperf.php` ajuda a criar antecipadamente todas as classes proxy que precisam ser geradas e o cache de varredura de anotações. Assim, ao iniciar em ambiente de produção não será necessário fazer a varredura novamente, o que otimiza bastante o tempo de inicialização e o uso de memória em produção. O exemplo abaixo não inclui o código do Dockerfile que não foi modificado.

```dockerfile
ENV TIMEZONE=${timezone:-"Asia/Shanghai"} \
    APP_ENV=prod \
    SCAN_CACHEABLE=(true)

COPY . /opt/www
RUN composer install --no-dev -o && php bin/hyperf.php

EXPOSE 9501

ENTRYPOINT ["php", "/opt/www/bin/hyperf.php", "start"]
```

Para usuários que não fazem deploy com `Docker`, é importante observar que, antes de reiniciar o serviço, é melhor executar uma vez `php bin/hyperf.php` e depois reiniciar o serviço, para reduzir o tempo gasto na reinicialização.

## Ajustar o arquivo de configuração config/config.php

Você precisa adicionar dois itens de configuração, `app_env` e `scan_cacheable`, em `config/config.php`. O exemplo de código abaixo não inclui outras configurações irrelevantes, conforme mostrado:

```php
<?php

return [
    // Em ambiente de produção use o valor prod
    'app_env' => env('APP_ENV', 'dev'),
    // Se deve usar o cache de varredura de anotações
    'scan_cacheable' => env('SCAN_CACHEABLE', false),
];
```

A configuração `scan_cacheable` controla se o cache de varredura de anotações será usado na inicialização da aplicação. Tanto o `Dockerfile` quanto o `config/config.php` acima possuem modificações relacionadas. Quando o valor dessa configuração é `true`, na inicialização do projeto será considerado que todas as classes já concluíram a varredura e geraram corretamente os caches e proxies correspondentes, pulando a fase de varredura para otimizar o tempo de inicialização e reduzir o consumo de memória.

## Modificar `config/autoload/logger.php`

Como a versão 2.0 elevou a versão da dependência do Monolog e, nas versões mais altas do Monolog, o formato de log padrão mudou, caso haja requisitos quanto ao formato do log, como a necessidade de integrar com sistemas de log com base no formato, você pode modificar o item de configuração `dateFormat` do arquivo de configuração `config/autoload/logger.php` para manter a consistência com as versões anteriores.

```php
<?php

declare(strict_types=1);

return [
    'default' => [
        'handler' => [
            'class' => Monolog\Handler\StreamHandler::class,
            'constructor' => [
                'stream' => BASE_PATH . '/runtime/logs/hyperf.log',
                'level' => Monolog\Logger::DEBUG,
            ],
        ],
        'formatter' => [
            'class' => Monolog\Formatter\LineFormatter::class,
            'constructor' => [
                'format' => null,
                'dateFormat' => 'Y-m-d H:i:s',
                'allowInlineLineBreaks' => true,
            ],
        ],
        'processors' => [
        ],
    ],
];

```

## Modificar `config/autoload/exceptions.php`

A versão 2.0 ajustou a lógica de tratamento de comportamentos anormais de rotas HTTP, como rota não encontrada (404) e método de requisição não correspondente (405), alterando uniformemente para lançar subclasses de exceção de `Hyperf\HttpMessage\Exception\HttpException` e, em seguida, gerenciar essas exceções de forma unificada através do ExceptionHandler, realizando o tratamento de resposta correspondente. Assim, o usuário também pode lançar as exceções correspondentes para obter uma experiência consistente de retorno de resposta. Contudo, como o ExceptionHandler é um mecanismo gerenciado pelo usuário, e na versão 1.1 o Skeleton padrão configurava uma classe `App\Exception\Handler\AppExceptionHandler` para fazer o tratamento de fallback das exceções e retornar uniformemente o código de status 500 ao cliente, você precisa configurar o `Hyperf\HttpServer\Exception\Handler\HttpExceptionHandler`, fornecido pela versão 2.0 para tratar HttpException, no arquivo de configuração `config/autoload/exceptions.php`, garantindo que esteja antes da configuração de `App\Exception\Handler\AppExceptionHandler`. O exemplo de configuração abaixo omite as configurações irrelevantes, conforme mostrado:

```php
<?php
return [
    'handler' => [
        'http' => [
            Hyperf\HttpServer\Exception\Handler\HttpExceptionHandler::class,
        ],
    ],
];
```

Após concluir a configuração do ExceptionHandler, você pode acessar diretamente uma rota inexistente; se o código de status da resposta for `404`, pode-se considerar que a modificação desta configuração foi concluída.

## Modificar o cliente gRPC

Para evitar conflitos de nomenclatura com o negócio real do gRPC, a versão 2.0 ajustou a nomenclatura das funções da classe base do cliente gRPC.

* `simpleRequest` -> `_simpleRequest`
* `clientStreamRequest` -> `_clientStreamRequest`
* `getGrpcClient` -> `_getGrpcClient`

Além disso, alguns métodos que não deveriam ser expostos tornaram-se métodos privados. Se o seu cliente gRPC envolve a chamada dos métodos acima, faça os ajustes de nomenclatura.

## Remover o listener de carregamento lazy do DI

Se o seu projeto usa a funcionalidade de carregamento lazy do componente DI, anteriormente era necessário registrar um listener `Hyperf\Di\Listener\LazyLoaderBootApplicationListener`, mas na versão 2.0 esse listener foi removido e você pode usar a funcionalidade diretamente. Portanto, se você usava essa funcionalidade anteriormente, é necessário remover o registro desse listener em `config/autoload/listeners.php`;

## Vincular a relação NormalizerInterface

Quando você usa a funcionalidade JSONRPC e a biblioteca `symfony/serializer` para fornecer a funcionalidade de serialização, como a versão 2.0 não mapeia mais automaticamente a classe de implementação de `Hyperf\Contract\NormalizerInterface`, você precisa adicionar manualmente essa relação de mapeamento, conforme abaixo:

```php
use Hyperf\Utils\Serializer\SerializerFactory;
use Hyperf\Utils\Serializer\Serializer;

return [
    Hyperf\Contract\NormalizerInterface::class => new SerializerFactory(Serializer::class),
];
```

## Ajustar as classes de implementação de Hyperf\Contract\ProcessInterface

O método `isEnable` em `Hyperf\Contract\ProcessInterface` recebeu um parâmetro `$server`, ou seja, `isEnable($server): bool`. Todas as classes de implementação de ProcessInterface precisam que você faça alguns ajustes nesse método.

## Verificar o arquivo config/autoload/aspects.php

Se você já fez algumas simplificações no Skeleton anteriormente, é necessário verificar se o arquivo `config/autoload/aspects.php` existe; caso não exista, é necessário adicionar um arquivo retornando um array vazio.

> Este problema será corrigido na 2.0.1; posteriormente não será necessário fazer essa verificação.

## Verificar o coletor de anotações personalizadas

Se você usa anotações personalizadas e usa um `Collector` personalizado para coletar os metadados das anotações, é necessário configurar o `Collector` correspondente em `annotations.scan.collectors`, porque no modo de desenvolvimento o framework julga se o arquivo foi modificado com base no tempo de modificação do arquivo e então decide se deve coletar novamente os metadados das anotações correspondentes. Portanto, quando `annotations.scan.collectors` não está configurado, a anotação só terá efeito na primeira inicialização do `server`.

Na camada de aplicação, essa configuração fica no arquivo `config/autoload/annotations.php`, conforme abaixo:

```php
<?php

return [
    'scan' => [
        'collectors' => [
            CustomCollector::class,
        ],
    ],
];
```

No componente, essa configuração é fornecida pelo ConfigProvider, conforme abaixo:

```php
<?php

return [
    'annotations' => [
        'scan' => [
            'collectors' => [
                CustomCollector::class,
            ],
        ],
    ]
];
```

## Iniciar o serviço e testar o acesso às interfaces

Ao usar a versão 4.5 do Swoole e o componente view, se ocorrer o problema de interface 404, você pode tentar remover o item de configuração `static_handler_locations` do arquivo `config/autoload/server.php`.

Os caminhos nessa configuração serão considerados rotas de arquivos estáticos, portanto, se `/` estiver configurado, todas as interfaces serão consideradas caminhos de arquivo, causando 404 nas interfaces.

## Concluir a atualização

Com isso, a atualização para a versão 2.0 está concluída. Porém, como todos os arquivos subjacentes do Hyperf podem ser reescritos através do DI, caso você tenha reescrito alguns arquivos internos do framework ajustados nesta atualização, ainda será necessário fazer alguns ajustes conforme sua situação real.  

Se você encontrar qualquer problema durante ou após a atualização, acesse [Github Issue](https://github.com/hyperf/hyperf/issues) para enviar sua issue explicando o problema encontrado, e ajudaremos você a resolver o mais breve possível.
